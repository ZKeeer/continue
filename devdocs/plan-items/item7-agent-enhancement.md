## 一、五个能力方向

| 方向           | 目标                                                                        |
| -------------- | --------------------------------------------------------------------------- |
| 计划约束化     | 让 agent 先计划、按计划执行、按阶段推进，而不是边想边乱调工具               |
| 结果结构化     | 让主 agent / sub-agent 的结果可被程序消费，而不是只能靠模型读自然语言总结   |
| 恢复机制化     | 让 agent 在超时、网络波动、工具失败、中断场景下能恢复或降级，而不是直接失败 |
| 验证强制化     | 让编辑后的编译、诊断、测试验证成为闭环中的硬门，而不是提示词建议            |
| 执行过程可视化 | 让用户能看清 agent 在做什么、做到哪一步、失败在哪里、是否值得继续           |

## 三、S 级项目

### 1. 计划合同化 Todo

**归属**：计划约束化

**当前状态**：S-1a 执行边界拦截已完成，见 [../archived/item7-agent-control-loop-first-batch.md](../archived/item7-agent-control-loop-first-batch.md)。完整步骤归属传播和阶段推进约束未实现，后续按 S-1b 跟踪。

**实现思路**：

- 将当前 `manage_todo_list` 从“建议调用”升级为主 agent / sub-agent 的执行合同
- 任务开始前必须先生成 3-7 步计划
- 每次工具调用必须归属到某个 todo step
- 未完成当前步骤时，不允许随意跨阶段推进
- 对“无计划直接开工”“步骤跳跃”“未收尾直接结束”做 runtime 拦截

**工作量（改动量）预估**：约 150-220 行

- `streamNormalInput.ts`：前置计划检查 + 执行阶段校验
- `sessionSlice.ts`：增加当前步骤、计划状态字段
- `callToolById.ts`：为工具调用挂步骤归属信息

**效果提升预估**：

- 多步骤任务完成率提升约 10%-18%
- 人工接管频次下降约 20%-30%

### 2. 阶段状态机与预算止损

**归属**：计划约束化

**当前状态**：S-2a 预算止损已完成，见 [../archived/item7-agent-control-loop-first-batch.md](../archived/item7-agent-control-loop-first-batch.md)。Research / Implement / Verify / Report 阶段状态机和 phase-aware tool whitelist 未实现，后续按 S-2b 跟踪。

**实现思路**：

- 将主循环显式拆分为 `Research`、`Implement`、`Verify`、`Report` 四个阶段
- 每个阶段约束可用工具集和退出条件
- 引入 token、wall-clock、tool-call 数三类预算
- 达到预算时，不是直接失败，而是输出当前进度、剩余风险和建议下一步

**工作量（改动量）预估**：约 220-350 行

- `streamNormalInput.ts`：增加阶段状态机和预算检查
- tool policy 评估处：按阶段切换工具白名单
- session state：增加阶段、预算消耗统计

**效果提升预估**：

- 复杂任务中的失控循环下降约 50%-70%
- 复杂任务完成率提升约 15%-25%

### 3. Sub-agent 结构化结果协议 v2

**归属**：结果结构化

**当前状态**：已完成并归档，见 [../archived/item7-agent-control-loop-first-batch.md](../archived/item7-agent-control-loop-first-batch.md) 和 [../archived/item7-subagent-enhancement-2026-04-30.md](../archived/item7-subagent-enhancement-2026-04-30.md)。

**实现思路**：

- 将 sub-agent 结果从当前“结构化 Markdown”升级为稳定协议
- 至少包含：`status`、`summary`、`evidence`、`filesModified`、`verificationRun`、`failureReason`、`nextRecommendedAction`
- 父 agent 优先消费协议字段，而不是再次让模型读自由文本总结
- 结果必须能区分 `completed`、`failed`、`incomplete`

**工作量（改动量）预估**：约 120-180 行

- `core/tools/implementations/subAgent.ts`：统一结果构造和状态枚举
- `core/tools/definitions/subAgent.ts`：更新 system message 和结果语义说明

**效果提升预估**：

- 父 agent 对 sub-agent 结果的误判下降约 50%-70%
- 重复搜索、重复读文件、重复修改下降约 20%-30%

### 4. 编辑后强制验证门

**归属**：验证强制化

**当前状态**：已完成并归档，见 [../archived/item7-agent-control-loop-first-batch.md](../archived/item7-agent-control-loop-first-batch.md)。当前实现优先自动调用 `get_problems`，仓库级 build/test/lint 模板仍按 A-10 跟踪。

**实现思路**：

- 只要发生 edit 类 tool call，系统自动进入验证阶段
- 优先调用 `get_problems`，其次执行仓库最窄的 `build/test/lint` 验证
- 验证失败后强制回到 fix 阶段，不允许直接宣告完成
- 验证通过后才进入报告阶段

**工作量（改动量）预估**：约 180-260 行

- `callToolById.ts`：识别 edit tool 完成后的自动续接逻辑
- `streamNormalInput.ts`：增加 verify gate
- 现有 verification skill：从提示词升级为 runtime 路由规则

**效果提升预估**：

- 改完即带编译错误的情况下降约 40%-60%
- 返工时长下降约 20%-35%

### 5. 瞬时错误自动退避重试

**归属**：恢复机制化

**当前状态**：已完成并归档，见 [../archived/item7-agent-control-loop-first-batch.md](../archived/item7-agent-control-loop-first-batch.md)。已落地 transient retry 与基础 failure class 注入；更完整的 fallback policy 仍按 A-7 跟踪。

**实现思路**：

- 将超时、429、网络抖动、临时文件锁、短暂 IDE 通信异常识别为 transient failure
- 对 transient failure 自动重试 1-3 次并指数退避
- 路径错误、schema 错误、权限错误视为 permanent failure，直接反馈模型修正
- 与当前 `toolErrorTracker` 结合，避免无限重复

**工作量（改动量）预估**：约 120-180 行

- `callToolById.ts`：增加错误分类和 retry policy
- core/tool 结果包装：透出更稳定的错误类别

**效果提升预估**：

- 瞬时错误导致的任务中断下降约 30%-50%
- 弱网和大仓库场景稳定性明显提升

## 四、A 级项目

### 6. Tool 边界检查点与 Resume

**归属**：恢复机制化

**实现思路**：

- 每次完成一个 tool call 或一个计划步骤后保存检查点
- 检查点至少包含：messages、todo 状态、当前阶段、关键产物、失败信息、验证结论
- 用户或系统恢复时从最近检查点继续，而不是整轮重做

**工作量（改动量）预估**：约 350-500 行

- `sessionSlice.ts`：持久化检查点结构
- `streamNormalInput.ts` / `callToolById.ts`：在 tool boundary 写入检查点
- session 加载逻辑：增加 resume 入口

**效果提升预估**：

- 长任务恢复成功率提升约 40%-60%
- 中断后的重复工作下降约 50%

### 7. 失败分类与自动降级策略

**归属**：恢复机制化

**当前状态**：基础 failure class 与 transient retry 已随 S-5 完成；自动降级策略仍未实现。

**实现思路**：

- 建立 failure class：`timeout`、`rate_limit`、`tool_schema`、`verification_fail`、`subagent_fail`、`permission_fail` 等
- 为每类失败定义 fallback policy
- 例如：timeout 拆子任务、verification_fail 回 fix、subagent_fail 主 agent 接手关键路径

**工作量（改动量）预估**：约 180-260 行

- `callToolById.ts`：错误分类
- `streamNormalInput.ts`：失败后续行动路由
- `subAgent.ts`：失败结果结构化输出

**效果提升预估**：

- 失败后可挽回的任务比例提升约 20%-35%

**工作量（改动量）预估**：约 150-220 行

**效果提升预估**：

- 用户审阅时间下降约 20%-30%

### 9. 执行树与步骤面板

**归属**：执行过程可视化

**实现思路**：

## 2026年4月22日 Claude Sonnet 4.6 评审结果

### 总体结论

**方向正确，但存在三类系统性问题：部分项目的技术可行性被高估；工作量估计普遍偏低 30-50%；多项存在对现有架构的错误假设。**

---

### 逐项评审

#### S-1 计划合同化 Todo — ⚠️ 核心设计目标无法在 runtime 实现

**根本问题**：Agent 循环是完全响应式的。`streamNormalInput.ts` 处理的是 LLM 已经决策后的输出，无法在 LLM 发出第一个非 todo 工具调用前"拦截"——你看到工具调用时已经太晚了。

"对无计划直接开工做 runtime 拦截"、"步骤归属信息"跨 GUI/Core IPC 边界追踪，这两点在当前架构下均不可行。

**实际可行范围**：在 `callToolById.ts` 检测首个非 todo 工具调用时 session 是否有 todo list，缺失则向模型注入提示（软约束，不是硬拦截）。真正的强约束只能通过 prompt 实现。

**建议**：降至 A 级，只做"首轮无计划时自动注入提示"的软检查。工作量估计从 150-220 行降至 80-120 行。效果提升预估也应下调至 5%-10%。

---

#### S-2 阶段状态机与预算止损 — ⚠️ 阶段感知依赖 LLM 主动配合

**根本问题**：系统如何确定 LLM 当前处于哪个阶段？除非 LLM 显式声明，代码只能做有限启发式推断（如检测到 edit tool 调用则认为进入 Implement 阶段）。"按阶段切换工具白名单"与现有 `allowedWithoutPermission` policy 体系存在冲突，需要整合。

**可行部分**：token/wall-clock/tool-call 三类预算计数完全可行，且价值高。四阶段模型建议仅用于 prompt 引导，不做 runtime 工具集切换。

**工作量修正**：仅预算部分约 100-150 行；若含阶段感知则 300-450 行（高于原估计）。

---

#### S-3 Sub-agent 结构化结果协议 v2 — ✅ 最可行，价值高，优先实施

这是 12 个项目中落地最干净的。当前 `buildResultContent()` 的 Markdown 是 v1，升级到含 `verificationRun`、`evidence`、`failureReason`、`nextRecommendedAction` 字段的 v2 只是扩展，无架构变更。

**注意**：`evidence` 字段需要子 agent 主动收集，`verificationRun` 字段依赖子 agent 确实执行了 `get_problems` / 测试命令。这两点需配合 `SUB_AGENT_SYSTEM_PREFIX` 指令更新才能生效。

**工作量**：120-180 行估计准确。**建议提升为第一优先**，因为它是 item 8（结果卡片）和 item 11（DAG 调度）的数据基础。

---

#### S-4 编辑后强制验证门 — ⚠️ "强制"只能是自动注入，非阻断

**根本问题**："验证失败后强制回到 fix 阶段，不允许直接宣告完成"是 prompt 约束，不是 runtime 约束。代码层面能做的是：edit tool 完成后自动追加 `get_problems` 结果注入到下一轮上下文，然后让 LLM 决策是否继续修复。

实现路径本身（在 `callToolById.ts` 识别 edit tool 完成后自动续接 `get_problems`）是可行的，180-260 行估计合理。

**建议**：将"强制"改为"自动触发验证并将结果注入上下文"，调整效果预估至 20%-35%（降幅）。

---

#### S-5 瞬时错误自动退避重试 — ✅ 最可行，ROI 最高，优先实施

`callToolById.ts` 已有 `trackToolError`、`hasReachedErrorLimit`、`formatEnhancedToolError` 完整基础设施。只需在此之上加错误分类枚举和 retry policy，120-180 行估计准确。

这是 12 个项目中**成本最低、收益最确定**的一项，建议与 S-3 并列为第一批。

---

#### A-6 Tool 边界检查点与 Resume — ❌ 工作量严重低估

350-500 行的估计**低了至少一倍**。`resume` 的核心难点不是保存检查点，而是重放：

- 从检查点恢复时 LLM 的上下文状态、`toolCallStates`、`applyStates` 需要完全一致重建

### 逐项复核

#### S-1 计划合同化 Todo — ⚠️ “只能软约束”不符合当前事实

**复核结论**：不完全成立。

- 不能阻止模型“生成”非 todo 工具调用
- 但可以阻止它“执行”非 todo 工具调用

### 对 S-1 保留意见的再评估

#### 结论

**部分接受。**

Claude 这次把问题收窄到了“步骤归属元数据”的跨边界成本，这个表述比上一轮准确。当前代码里，工具真正跨 GUI/Core 的执行协议是 `tools/call`，载荷只有 `toolCall`；而执行边界控制、tool state 更新、todo widget 落盘都在 GUI 侧完成。因此：

- 如果一期目标只是“无计划时阻断首个非 todo 工具执行”，那不需要新增 IPC 负担

- 在 `callToolById.ts` 执行前检查 `todoListItems`

- 若后续要让 core 侧日志、resume、sub-agent 协议也消费，则再扩 IPC 载荷

这一版复杂度比 S-1a 高，Claude 上调到 200-280 行是合理的。

- 不接受“因为步骤归属更复杂，所以 S-1 降级”
- 接受“需要把 S-1 拆成两阶段，并上调增强版工作量估计”

### 对 S-2 保留意见的再评估

#### 结论

**接受。**

Claude 提醒的冲突点是实际存在的。当前 `evaluateToolPolicies.ts` 已经把 edit tool 直接视为 `allowedWithoutPermission`，其他工具则走 `basePolicy + dynamicPolicy` 合并逻辑。如果再额外引入“按阶段切换工具白名单”，就会遇到两个问题：

- 阶段策略与用户配置/动态安全策略冲突时，谁优先

- 不接受把这一冲突外推为“S-2 不能先做”

在这个口径下，当前路线图可以继续推进，不需要再改动优先级排序，只需要把两个项目的一期定义写得更窄、更硬。

## 2026年4月22日 最终总结与可执行计划

### 最终总结

这轮讨论之后，路线图已经收敛到一个可以直接开工的版本。

核心结论只有三条：

1. **第一批只做最短闭环，不做结构性大改。**
2. **先解决“结果能读懂、错误能恢复、改后会验证、开工前有计划”这四个直接决定完成率的问题。**
3. **所有需要扩大状态结构、改造 policy 链路、引入恢复/回放/并行调度的能力，全部后移。**

因此，当前最合理的实施顺序不是“把 12 项都平推”，而是先完成 4 个最小闭环能力：

- S-3 `Sub-agent 结构化结果协议 v2`
- S-5 + A-7 `瞬时错误自动退避重试 + 失败分类`
- S-4 `编辑后验证 gate`
- S-1a `计划执行边界拦截`

这 4 项完成后，agent 的核心能力会从“能调工具”提升到“能在工程任务里更稳定地交付结果”。

---

### 是否符合第一性原理

**结论：符合。**

按第一性原理拆解，agent 要想“高效干活”，底层只依赖 4 个不可再约简的问题：

1. **是否知道当前要做什么**
2. **是否能可靠执行动作**
3. **是否能判断动作结果是否有效**
4. **是否能在失败后恢复，而不是整轮报废**

当前收敛后的第一批能力，分别对应这 4 个基础问题：

- S-1a 解决“没有计划就乱开工”
- S-5 + A-7 解决“工具失败就断流”
- S-4 解决“修改后没有验证闭环”
- S-3 解决“上级 agent / 用户无法稳定消费执行结果”

也就是说，这个计划不是从“做哪些炫功能”出发，而是从“完成一次真实任务至少需要什么”出发，符合第一性原理。

不完全属于第一性原理核心层的能力有：

- A-8 结果卡片
- A-9 执行树
- B-12 运行回放

这些能力仍然有价值，但它们更偏“可审计性和接管体验增强”，不该先于基础闭环落地。

---

### 是否符合奥卡姆剃刀

**结论：在当前收敛版本下，符合。**

奥卡姆剃刀要求的是：在能解释问题并解决问题的前提下，不额外引入更复杂的结构。

当前计划满足这一点，原因是：

1. **不先改 `history` 基础结构**，执行树先走“扁平 history + 索引字段”方案
2. **不先做 checkpoint/resume**，因为它不是最小闭环必需项
3. **不先做 phase-aware whitelist**，预算止损先独立落地
4. **不先把步骤归属穿透到所有 IPC/日志/恢复链路**，先做执行边界拦截版
5. **不先做 DAG 调度**，因为没有结构化结果和稳定计划表达时并行只会放大复杂度

换句话说，这版计划不是“先建一套完整系统再使用”，而是“先做最小可用控制面，再逐层外扩”。这符合奥卡姆剃刀。

如果偏离当前收敛口径，以下做法就会违背奥卡姆剃刀：

- 在第一批里直接上完整步骤归属传播
- 在第一批里直接上阶段白名单切换
- 在第一批里直接上执行树底层重构
- 在第一批里直接上 resume / DAG / replay

**目标**：让 sub-agent 的结果变成稳定协议，而不是自由文本。

#### 阶段 2：做 S-5 + A-7 错误分类与自动恢复

- transient failure 自动重试 1-3 次
- permanent failure 直接反馈模型修正
- 与现有重复错误上限控制兼容

**验收标准**：

- 同一类瞬时错误会自动重试
- 路径错误、schema 错误、权限错误不会被误判为可重试
- 超过上限后 agent 正常停下，不会死循环

#### 阶段 3：做 S-4 编辑后验证 gate

**目标**：编辑完成后系统先验证，再继续后续流程。

- `gui/src/redux/thunks/streamNormalInput.ts`
- 视具体接入点决定是否补充 `streamResponseAfterToolCall.ts`

**最小交付**：

- edit tool 完成后自动触发一轮验证

- 验证结果先进入上下文，再决定是否继续

**验收标准**：

- 编辑类 tool call 后不再直接进入“已完成”陈述
- 验证失败时会产生明确的 fix 信号回注

#### 阶段 4：做 S-1a 计划执行边界拦截

**目标**：没有 todo 计划时，不允许执行首个非 todo 工具。

**改动文件**：

- `gui/src/redux/thunks/callToolById.ts`
- `gui/src/redux/slices/sessionSlice.ts`

**验收标准**：

- 模型即使先生成了非 todo 工具调用，也不能直接执行
- 一旦 todo 存在，后续工具执行恢复正常

#### 阶段 5：做 S-2a 预算止损

**目标**：避免长任务在主循环里失控空转。
