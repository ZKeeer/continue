# PyCharm 自动补全 IPC 瓶颈修复 (2026-04-13 ~ 04-17)

## 背景

在 Batch 1-2 (2026-03-23 ~ 04-10) 中完成了 QueueManager 接入、prefilter IPC 缓存、HelperVars 诊断计时等优化后，
PyCharm 端自动补全仍然存在严重的 IPC 阻塞问题，尤其在 Windows 上表现为：

- 用户连续输入时，自动补全完全无响应（"卡死"状态）
- Linux 上偶尔出现短暂无响应，Windows 上复现概率高得多
- 日志中大量 `core.handler.result hasOutcome=false` 和 `completion-service.response len=0`
- 141 次 autocomplete 请求仅 3 次返回结果

## 根因分析

### 问题 1: 缺少 abort 信号传播 → 请求泄漏

**现象**: IntelliJ 端用户取消补全请求后，Core 端的 `autocomplete/complete` handler 仍在执行，消耗 LLM 资源和 IPC 带宽。

**根因**:

- `core.ts` 中 `autocomplete/complete` handler 未创建 `AbortController`，传入的 signal 为 `undefined`
- IntelliJ 端 `ContinueCompletionService` 在请求超时/取消时没有向 Core 发送 abort 消息
- 结果：旧请求在 Core 端持续运行，占用 LLM 连接，其响应通过 IPC 管道回传，挤占带宽

**影响链**:

```
用户输入 → 旧请求未取消 → Core 端多个 LLM 请求并行 → 响应堆积在 IPC 管道
→ 管道拥塞 → 新请求的 IDE 反向请求也被阻塞 → 完全无响应
```

### 问题 2: Windows pipe 缓冲区小 → 写入阻塞

**现象**: Windows 上 IPC 管道写入阻塞，Linux 上不明显。

**根因**:

- Windows 命名管道默认缓冲区仅 4KB（Linux 通常 64KB+）
- Node.js 的 `process.stdout.write()` 在 Windows 上是同步阻塞的
- 当 Core 端有大量响应消息排队时，`process.stdout.write()` 阻塞事件循环
- 反向 IDE 请求（如 `readFile`、`getWorkspaceDirs`）的响应必须经过同一管道
- 造成潜在死锁：Core 等待 IDE 响应 → IDE 响应排队在管道中 → 管道被其他消息占满

**影响链**:

```
多个 LLM 响应同时回传 → stdout.write() 阻塞 → 事件循环卡住
→ IDE 反向请求无法处理 → Core 等待 IDE 响应超时 → 整体无响应
```

### 问题 3: IntelliJ 端 limitedDispatcher 并发限制

**现象**: IDE 反向请求处理慢，排队等待。

**根因**:

- `IdeProtocolClient.kt` 中 `limitedDispatcher = Dispatchers.IO.limitedParallelism(4)`
- 并发 IDE 请求（readFile、getWorkspaceDirs 等）被限制为 4 个并行
- 当 Core 端多个 autocomplete 请求同时发起 IDE 请求时，后续请求排队

### 问题 4: 请求去重缺失

**现象**: 同一 IDE 方法被多个 autocomplete 请求重复调用。

**根因**:

- 每次 `autocomplete/complete` 都会独立发起 `getWorkspaceDirs`、`readFile`、`getDocumentSymbols` 等 IDE 请求
- 没有请求去重机制，相同参数的请求被重复发送

### 问题 5: 旧请求未清理

**现象**: 新的 autocomplete 请求被旧的待处理请求阻塞。

**根因**:

- `CoreMessenger.kt` 中 `responseListeners` 不会清理旧的 autocomplete 响应监听器
- `ContinueProcessHandler.kt` 中 `writeQueue` 不会清理旧的待发送消息
- 旧的 IDE 请求（由 Core 发起的反向请求）也不会被取消

### Phase 6: IpcMessenger 异步写入 + 背压管理

**文件**: `binary/src/IpcMessenger.ts`

将 `process.stdout.write()` 从同步改为异步队列写入，避免阻塞事件循环：

```typescript
private _writeQueue: string[] = [];
private _writing = false;
private _drainWaiters: (() => void)[] = [];

private async _drain(): Promise<void> {
    return new Promise<void>((resolve) => {
        const canWrite = process.stdout?.write("");
        if (canWrite !== false) { resolve(); return; }
        this._drainWaiters.push(resolve);
        process.stdout?.once("drain", () => {
            const waiters = this._drainWaiters.splice(0);
            waiters.forEach((w) => w());
        });
    });
}

private async _flushQueue() {
    if (this._writing) return;
    this._writing = true;
    try {
        while (this._writeQueue.length > 0) {
            const data = this._writeQueue.shift()!;
            const canWrite = process.stdout?.write(data);
            if (canWrite === false) { await this._drain(); }
        }
    } catch (e) {
        console.error("[IpcMessenger] Write error:", e);
    } finally {
        this._writing = false;
    }
}

_sendMsg(msg: Message) {
    const d = JSON.stringify(msg) + "\r\n";
    this._writeQueue.push(d);
    void this._flushQueue();
}
```

async delayAndShouldDebounce(debounceDelay: number): Promise<boolean> {
    const fixedDelay = Math.max(60, debounceDelay);
    const requestId = uuidv4();
    this.currentRequestId = requestId;
    if (this.debounceTimeout) clearTimeout(this.debounceTimeout);
    return new Promise<boolean>((resolve) => {
        this.debounceTimeout = setTimeout(() => {
            const shouldDebounce = this.currentRequestId !== requestId;
            if (!shouldDebounce) this.currentRequestId = undefined;
            resolve(shouldDebounce);
        }, fixedDelay);
    });
}

## 安全分析

- **VS Code 不受影响**: VS Code 不通过 Core 发送 `autocomplete/complete`，Core 端的 AbortController 和 IPC 缓存对 VS Code 侧无影响
- **TCP 仅在 Windows 启用**: Linux/macOS 继续使用 stdin/stdout pipe，不受 TCP 相关代码影响
- **TCP fallback**: 如果 TCP 连接失败，会 fallback 到 stdin/stdout pipe（需确认当前代码是否已实现）
- **缓存 TTL 合理**: `getIdeInfo` 永久缓存（运行时不变）、`getWorkspaceDirs` 30s（工作区目录极少变化）、`getRepoName` 60s
- **请求去重安全**: 同类型请求取消旧的、保留最新的，符合 autocomplete 语义

## 已知问题与待解决

### ~~TCP 模式未生效~~ → 已回退到 IPC (2026-04-15)

**决策**: TCP 模式实现存在多个问题（端口占用、进程协调、日志混淆），鉴于 IPC + abort 机制已能有效解决 Windows 阻塞问题，决定回退到 IPC 模式。

**回退内容**:

- `binary/src/index.ts`: `useTcp = false`
- `extensions/intellij/.../continue/CoreMessenger.kt`: `isTcp = false`

**保留的关键机制**:

1. **Core 端 abort 信号传播**: `core.ts` 中 `autocomplete/complete` 使用 `AbortController`
2. **IpcMessenger 异步写入 + 背压管理**: `_writeQueue` + `_drain()` + `_flushQueue()` 避免 `stdout.write()` 阻塞
3. **IntelliJ 端 abort 信号传播**: `ContinueCompletionService.sendAbort()` + `cancelAutocomplete()`
4. **请求队列清理**: `CoreMessenger` 在新请求时调用 `cancelPendingIdeRequests()` + `clearPendingWrites()`
5. **IDE 方法 IPC 缓存**: `messageIde.ts` 中 `getIdeInfo`、`getWorkspaceDirs`、`getRepoName` 缓存

**为什么 IPC + abort 机制足够**:

根本问题是旧请求未取消导致的管道拥塞。通过 abort 机制取消旧请求后：

- Core 端不再累积多个 LLM 响应
- IPC 管道不再拥塞
- IpcMessenger 异步写入队列 + 背压管理作为安全网
- 即使在 Windows 4KB 缓冲区下也能正常工作

**TCP 代码保留但禁用**: `TcpMessenger.ts` 和 `ContinueSocketProcess.kt` 保留，便于未来需要时启用。

### Queue Fast-Path 仍有 ~300ms 延迟 → 修复 (2026-04-15)

**现象**: 即使 queue-fast-path 被触发，`snippetCollectionMs` 仍然是 ~300ms。

**根因**:

```typescript
if (this.queueManager && this.queueManager.isReady(input.filepath)) {
  const queuePayload = this.queueManager.toSnippetPayload(...); // <1ms ✓
  const rootPathSnippets = await this.contextRetrievalService.getRootPathSnippets(helper); // 150-200ms ✗
  // ...
}
await this.enrichSnippetPayload(...); // 100-150ms ✗
```

Queue fast-path 分支仍然调用了两个昂贵的 IPC 操作：

| 操作                     | 耗时   | 原因                                                     |
| ------------------------ | ------ | -------------------------------------------------------- |
| `getRootPathSnippets()`  | ~150ms | 调用 `gotoDefinition` IPC，150ms timeout                 |
| `enrichSnippetPayload()` | ~100ms | 调用 `definitionCacheService.getDefinitionsForContext()` |

**修复**:

在 queue-fast-path 中跳过这些耗时操作，仅使用 queue 中已预收集的数据：

```typescript
if (this.queueManager && this.queueManager.isReady(input.filepath)) {
  const queuePayload = this.queueManager.toSnippetPayload(...); // <1ms
  // Skip getRootPathSnippets IPC - use local scopeSummary instead
  const scopeSnippet = helper.getScopeSummarySnippet(); // <1ms (already computed)
  const rootPathSnippets = scopeSnippet ? [scopeSnippet] : [];
  snippetPayload = { rootPathSnippets, ...queuePayload };
  usedFastPath = true;
}

// Skip enrichSnippetPayload in fast-path
if (!usedFastPath) {
  await this.enrichSnippetPayload(...);
}
```

**预期效果**:

| 指标                              | 修复前 | 修复后     |
| --------------------------------- | ------ | ---------- |
| `snippetCollectionMs` (fast-path) | ~300ms | **~5ms**   |
| `totalContextMs` (fast-path)      | ~500ms | **~100ms** |

### IpcMessenger.\_drain() 探测写入问题

`_drain()` 方法通过 `process.stdout.write("")` 探测缓冲区状态，空字符串写入在实践中工作正常。
如果未来出现问题，可考虑使用 `process.stdout.writableNeedDrain` 属性。

## 架构对比：修复前 vs 修复后

### 修复前

```
用户输入 → IntelliJ 发送 autocomplete/complete
  → Core 启动 LLM 请求（无 abort signal）
  → 用户继续输入 → IntelliJ 发送新的 autocomplete/complete
  → 旧请求仍在 Core 端运行 → LLM 响应回传
  → 多个响应堆积在 IPC 管道（Windows 4KB 缓冲区）
  → process.stdout.write() 阻塞事件循环
  → IDE 反向请求无法处理 → Core 等待 IDE 响应超时
  → 整体无响应
```

### 修复后

```
用户输入 → IntelliJ 发送 autocomplete/complete
  → Core 启动 LLM 请求（带 abort signal）
  → 用户继续输入 → IntelliJ:
    1. cancelAutocomplete() → 发送 abort + cancel
    2. 清理 responseListeners 中旧的 autocomplete 监听器
    3. cancelPendingIdeRequests() → 取消旧的 IDE 反向请求
    4. clearPendingWrites() → 清理写入队列
    5. 发送新的 autocomplete/complete
  → Core 收到 abort → 取消旧请求 → 释放 LLM 资源
  → 新请求独占 IPC 通道 → 响应及时返回
  → IpcMessenger 异步写入 + 背压管理 → 无写入阻塞
  → IDE 方法缓存 → 减少 IPC 往返
```

## Phase 9: NuProcess 替代默认 IPC + TCP 修复 + Abort 增强 (2026-04-15)

### 9.1 NuProcess 替代默认 IPC

**问题**: Java `ProcessBuilder` 在 Windows 上使用匿名管道（4KB buffer），导致大消息写入阻塞。
虽然 Phase 6 中 IpcMessenger 异步写入缓解了 TS 端阻塞，但 Kotlin 端 `BufferedReader.readLine()` 仍受限于 OS 管道缓冲区。

**方案**: 引入 [NuProcess](https://github.com/brettwooldridge/NuProcess) (v2.0.6, ~60KB)，
底层使用 IOCP(Windows) / epoll(Linux) / kqueue(macOS) 实现非阻塞子进程 I/O。

**新文件**: `ContinueNuProcess.kt`

| 组件                   | 实现                                                   |
| ---------------------- | ------------------------------------------------------ |
| `onStdout(ByteBuffer)` | 回调 → `PipedOutputStream` → `PipedInputStream`(256KB) |
| `output: OutputStream` | 自定义包装 `NuProcess.writeStdin(ByteBuffer)`          |
| `onExit(statusCode)`   | 关闭管道 + 触发 `onUnexpectedExit` + 错误上报          |
| 权限设置               | 复用原有 `setPermissions()` 逻辑                       |

**架构选择**: 保留 `ContinueProcess` 接口不变，`ContinueProcessHandler` 无感切换。

### 9.2 IpcMode 枚举

`CoreMessenger.kt` 新增 `IpcMode` 枚举：

```kotlin
enum class IpcMode {
    NUPROCESS,  // 默认: NuProcess IOCP/epoll/kqueue
    TCP         // TCP loopback，动态端口协商
}
```

通过环境变量 `CONTINUE_IPC_MODE` 控制，默认 `NUPROCESS`。
去掉了原来的 PIPE 模式（被 NUPROCESS 完全替代）。

### 9.3 TCP 模式修复

TCP 模式之前实测存在多个问题，本次修复：

| 问题                                                       | 修复                                                                 |
| ---------------------------------------------------------- | -------------------------------------------------------------------- |
| 端口硬编码 3000，冲突风险高                                | `TcpMessenger` 改为 `listen(0)` 让 OS 分配空闲端口                   |
| IntelliJ 不知道 binary 监听的端口                          | binary 启动后通过 stderr 输出 `TCP_PORT:<port>`，Kotlin 读取解析     |
| `useTcp` 硬编码 false                                      | 改为读取 `USE_TCP` 环境变量，由 `CoreMessenger` 在启动 binary 时注入 |
| buffer 128KB 偏小                                          | 全部上调到 256KB                                                     |
| `ContinueBinaryProcess.onUnexpectedExit` 在 TCP 模式误触发 | 保留（TCP 模式下 binary 退出确实需要 restart）                       |

### 9.4 Buffer 统一 256KB

| 位置                                             | 之前       | 之后  |
| ------------------------------------------------ | ---------- | ----- |
| `ContinueNuProcess` PipedInputStream             | —          | 256KB |
| `ContinueSocketProcess` sendBuffer/receiveBuffer | 128KB      | 256KB |
| `ContinueProcessHandler` BufferedReader          | 8KB (默认) | 256KB |

### 9.5 Debounce 上限 200ms

| 位置                              | 之前                      | 之后                         |
| --------------------------------- | ------------------------- | ---------------------------- |
| `Debouncer.kt` (IntelliJ)         | `max(120, config)` 无上限 | `max(120, min(config, 200))` |
| `AutocompleteDebouncer.ts` (Core) | `max(60, config)` 无上限  | `max(60, min(config, 200))`  |

### 9.6 Abort 增强 (方案B)

**之前**: `cancelAutocomplete()` 同时发送 `abort(messageId)` + `autocomplete/cancel`。
Core 端 `cancel()` 会清除所有 completionId 的 AbortController，包括 prefetch 等缓存机制。

**之后**: `cancelAutocomplete()` 只发送 `abort(messageId)`，不发 `autocomplete/cancel`。

| 效果         | 说明                                                       |
| ------------ | ---------------------------------------------------------- |
| 精准取消     | 只停止指定 messageId 的 LLM 调用和 IPC 传输                |
| 保留缓存     | Core 端 CompletionProvider 内部缓存（prefetch 等）继续存活 |
| 加速下次补全 | 缓存的补全结果可用于下次请求的 cache check                 |
