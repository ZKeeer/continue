## 代码审查修复记录 (2026-03-24)

以下修复基于 Opus 4.6 × GPT 5.4 联合审查结论（详见 `conversation_results.md`）。

### Fix #1 [高优]: 缓存键语义修复

- **问题**: cache READ 使用 `helper.prunedPrefix`（原始文档前缀），cache WRITE 使用 `outcome.prefix`（模板编译后的 prompt 前缀）。SQL `WHERE ? LIKE key || '%'` 语义下永远不可能命中。**此为上游 bug（`bd353e06d` 已存在），zkdev 继承并放大了它。**
- **修复**:
  - `AutocompleteOutcome` 新增 `documentPrefix` / `documentSuffix` 字段（原始文档前缀/后缀）
  - cache WRITE 改用 `outcome.documentPrefix`，与 READ 的 `helper.prunedPrefix` 一致
  - `PrefetchService` 和 `_cacheSimlarEditPredictions` 均改用 `documentPrefix` 计算缓存键
- **影响**: 缓存系统现在能正确命中，所有基于缓存的预测功能（Prefetch、SimilarEdit）有了正确的工作基础

### Fix #2 [高优]: 超时并发控制

- **问题**: `racePromise()` 只是 `Promise.race`，放弃等待但不取消底层 LSP/IO 请求。连续输入时会堆积无限失效请求，加重 IDE 后台负载。
- **修复**: 添加 `_pendingSnippetRequests` 计数器和 `MAX_PENDING_SNIPPET_REQUESTS=3` 上限。超限时直接返回空结果，避免堆积。
- **局限**: IDE 接口（`gotoDefinition` 等）不接受 `AbortSignal`，真正的取消需要上游支持。当前只是防堆积，不是真取消。

### Fix #3 [高优]: 参数恢复保守默认值

- **问题**: 针对 sglang + qwen3-coder + A100 的实验参数被设为全局默认值，影响所有用户/模型/环境。
- **修复**:
  - 恢复上游保守默认值（`maxPromptTokens: 1024`, `debounceDelay: 350` 等）
  - 删除仓库内置 zkdev 特化 preset，保留通过 `tabAutocompleteOptions` 显式配置覆盖默认值的正式入口
  - 新增 `experimental_enablePrefetch`, `experimental_enableEditIntentDetection`, `experimental_enableSimilarEditDetection` 三个实验开关，默认关闭

### Fix #4 [中高优]: SimilarEditDetector 不再排除相同补全

- **问题**: `areEditsSimilar()` 排除了 `a.completion.trim() === b.completion.trim()` 的情况，恰好封堵了最常见的批量编辑场景（多处加同一参数、同一日志等）。
- **修复**: 移除 identical completion 排除逻辑。缓存键修复后，去重由缓存系统自然处理。

### Fix #5 [中优]: NextEdit autodetect 收缩匹配范围

- **问题**: `MODEL_SUPPORTS_GENERIC_NEXT_EDIT = ["qwen"]` 子串匹配，导致所有 qwen 模型启用 NextEdit，但只验证过 qwen3-coder。
- **修复**: 收缩为 `["qwen3-coder"]`，仅匹配已验证的模型。

### Fix #6 [中优]: Prefetch 加实验开关

- **问题**: 每次 accept 补全都触发后台预取推理请求，无速率限制、无配置开关。
- **修复**: 添加 `experimental_enablePrefetch` 开关（默认 false），需要用户通过 `tabAutocompleteOptions` 显式启用。

### Fix #7 [中优]: EditIntentDetector 加实验开关

- **问题**: 在 `getAllSnippets` 中无条件调用，无法关闭。
- **修复**: 添加 `experimental_enableEditIntentDetection` 开关（默认 false），由 `getAllSnippets` 和 `getAllSnippetsWithoutRace` 检查。

### Fix #9 [低优]: temperature=0 策略说明

- temperature=0 是 autocomplete 场景的业界惯例（GitHub Copilot、Codeium 等均使用低温或零温）
- 确定性输出有利于缓存命中和一致性体验
- **权衡**: 可能降低探索性候选的多样性，不适合需要创造性补全的场景
- 用户可通过 `tabAutocompleteOptions.completionOptions.temperature` 覆盖

### Fix #10 [低优]: truncateAtBlockBoundary 命名澄清

- `truncateAtBlockBoundary()` 实际是**行级正则启发式**，不是真正的 AST 分析
- 使用 `BLOCK_START_PATTERN` 正则匹配 function/class/export/def 等关键字来猜测块边界
- 比 tree-sitter AST 轻量但精度有限，建议后续改名或添加注释标注

## ✅ 已完成优化 (2026-03-24) — 上下文关联性 + Token 预算

### 上下文优先级重排

基于各上下文源的关联强度分析，重排 snippet 优先级，核心策略：**"编辑 > 光标 > Tab > diff"**。

- **文件**: `templating/filtering.ts`
- **变更**: snippetConfigs 优先级重排

| 上下文源              | 旧优先级     | 新优先级 | 理由                             |
| --------------------- | ------------ | -------- | -------------------------------- |
| recentlyEditedRanges  | 4            | **1**    | 用户刚改过的代码 = 最强任务信号  |
| recentlyVisitedRanges | 3            | **2**    | 光标停留±20行 = "Tab+光标"融合   |
| recentlyOpenedFiles   | 2            | **3**    | 降为回退：无光标数据的Tab取全文  |
| clipboard             | 1 (disabled) | **90**   | 信噪比低，默认关闭               |
| diff                  | 5            | **98**   | 常太大太杂，降至最低(仅在base前) |
| base                  | 99           | 99       | 不变                             |

**"Tab文件+光标"自动融合** — 利用已有去重机制零成本实现：

1. `RecentlyVisitedRangesService`(VSCode层) 追踪每个Tab的光标位置(±30行)
2. visitedRanges(优先级2) 先处理 → 添加光标附近代码
3. openedFiles(优先级3) 后处理 → `formatOpenedFilesContext` 自动跳过已被visitedRanges覆盖的文件
4. **效果**: 有光标数据的Tab → 光标附近内容；无光标数据的Tab → 文件头部内容

### editedRanges+visitedRanges 同文件互补

- **文件**: `templating/filtering.ts`
- **问题**: editedRanges先添加文件X的小编辑片段(5-10行)，visitedRanges想添加相同文件X的大光标上下文(60行)会被filepath去重跳过
- **修复**: 引入 `editedRangesFilepaths` 追踪集合，visitedRanges 过滤时对editedRanges已添加的文件放行
- **效果**: 同一文件可同时有编辑片段(精确修改内容)+光标上下文(周围代码)，互补而非互斥

### 语法关联上下文（import/AST）在 prompt 中的位置

语法结构信息通过 `base` snippets（优先级99）注入 prompt：

| 语法源               | 实现                                                                       | 注入方式                   |
| -------------------- | -------------------------------------------------------------------------- | -------------------------- |
| import 类型/接口定义 | `ImportDefinitionsService.ts`: 解析 import → LSP gotoDefinition → 取签名   | `importDefinitionSnippets` |
| 当前文件引用符号定义 | `RootPathContextService.ts`: tree-sitter AST → LSP gotoDefinition → 取定义 | `rootPathSnippets`         |
| 编辑意图（实验）     | `EditIntentDetector.ts`: 分析编辑模式 → 生成意图描述                       | `staticSnippet`            |

优先级99虽然数字最大，但语义是"在所有行为信号（编辑/光标/Tab）分配完后，用剩余token预算填入"。
这确保语法结构信息始终被包含，且不挤占更高优先级的行为上下文。

### RecentlyVisitedRangesService 扩容

- **文件**: `extensions/vscode/src/autocomplete/RecentlyVisitedRangesService.ts`
- **变更**: `maxRecentFiles: 3 → 5`
- **理由**: 追踪更多文件的光标位置，配合优先级重排扩大光标上下文覆盖

### maxPromptTokens 提升

- **文件**: `core/util/parameters.ts`
- **变更**: `DEFAULT_AUTOCOMPLETE_OPTS.maxPromptTokens: 1024 → 4096`
- **理由**: 原值 1024 导致 snippet 空间几乎为零(prefix+suffix 已占大半)。4096 是 Copilot 级别，平衡质量与延迟
- **覆盖**: 用户可通过 `config.yaml` 的 `tabAutocompleteOptions.maxPromptTokens` 覆盖

### Tab 文件 snippet 参数调整

- **文件**: `templating/formatOpenedFilesContext.ts`
- **变更**:
  | 参数 | 旧值 | 新值 | 理由 |
  |---|---|---|---|
  | defaultNumFilesUsed | 5 | 7 | 4096预算下纳入更多Tab文件 |
  | recencyWeight | 0.6 | 0.7 | 强化最近打开文件优先级 |
  | sizeWeight | 0.4 | 0.3 | 配合recency提升 |
  | minTokensInSnippet | 125 | 200 | 每个文件分到更有意义的内容量 |

## ⚠️ 已完成优化 (2026-03-24) — Prompt + 预测功能（待验证）

> 以下功能方向判断合理，但收益尚未经严格 A/B 测试验证。预测功能（Prefetch/EditIntent/SimilarEdit）现已置于实验开关之后，默认关闭。

### Prompt-1: qwen3-coder 多文件 FIM 模板 (#13, #14)

- **文件**: `templating/AutocompleteTemplate.ts`
- **问题**: 所有 snippet 用 `// ` 注释包裹，浪费 30-40% snippet token 预算；未使用 qwen3-coder 原生多文件 token
- **修复**: 新建 `qwenCoderMultifileFimTemplate`，使用 `compilePrefixSuffix` 模式:
  - snippet 格式: `<|file_sep|>filepath\ncode` (替代 `// Path: filepath\n// code`)
  - 加入 `<|repo_name|>` token 提供仓库上下文
  - 保留 `qwenCoderFimTemplate` 作为回退
- **影响范围**: 仅 qwen-coder 系列模型；其他模型走原有 comment 包裹路径
- **预期**: snippet token 开销降低 ~49%，等效增加 2-3 个 snippet 上下文量

### Prompt-2: snippet 稳定排序 (#15)

- **文件**: `templating/filtering.ts`
- **问题**: `shuffleArray()` 随机打乱 base snippets，破坏 sglang RadixAttention 前缀缓存
- **修复**: 替换为 `sortByFilepath()` 按文件路径稳定排序
- **预期**: sglang prefix cache 命中率显著提升，减少 TTFT

### Prompt-3: diff snippet 限流 (#16)

- **文件**: `templating/filtering.ts`
- **问题**: diff snippets 可能非常大，挤占 import 定义和 root path 等高价值上下文
- **修复**: diff snippets 最多消耗总 snippet token 预算的 30%

### P0: 补全预取 (Predictive Prefetch) (#17) ⚠️ 实验功能

- **文件**: `prediction/PrefetchService.ts`, `CompletionProvider.ts`
- **功能**: 用户接受补全后，后台预生成新光标位置的下一个补全
- **状态**: 默认关闭，需通过 `experimental_enablePrefetch: true` 启用
- **实现**:
  - `PrefetchService.prefetchAfterAccept()`: 50ms 延迟后计算新 prefix，构建轻量 prompt，调用 LLM
  - 使用 `AbortController` 管理生命周期，新请求或 cancel 时中止
  - 结果存入 `AutocompleteLruCache`，下次真实请求命中缓存
  - maxTokens=256 限制预取成本
- **集成**: `CompletionProvider.accept()` 触发（仅当 flag 启用时），`cancel()` 中止
- **待验证**: 需要统计 prefetch 触发次数、实际缓存命中率、无效请求比例

### P1: 行级预取缓存 (#18)

- **说明**: 由 P0 吸收——prefetch 生成的补全可能跨多行（maxTokens=256），已覆盖后续数行

### P1: 编辑意图检测 (#19) ⚠️ 实验功能

- **文件**: `prediction/EditIntentDetector.ts`, `snippets/getAllSnippets.ts`
- **功能**: 分析最近编辑的代码，检测重复编辑模式（如批量添加 try/catch、添加类型注解等），生成意图描述注入 prompt
- **状态**: 默认关闭，需通过 `experimental_enableEditIntentDetection: true` 启用
- **实现**:
  - 12 种内置意图模式（error handling, async/await, type definitions 等）
  - 跨编辑符号重复检测（同一符号在 2+ 次编辑中出现）
  - 生成 `AutocompleteStaticSnippet` 注入 snippet pipeline
  - 只在 120 秒内 2+ 次编辑匹配时触发（避免噪音）
- **集成**: `getAllSnippets()` 和 `getAllSnippetsWithoutRace()` 在 flag 启用时包含
- **待验证**: 对补全质量的实际影响需要离线评估或 A/B 测试

### P2: qwen3-coder NextEdit (#20) ⚠️ 实验功能

- **文件**: `nextEdit/providers/GenericFimNextEditProvider.ts`, `nextEdit/NextEditProviderFactory.ts`, `llm/autodetect.ts`
- **功能**: 为非 Mercury/Instinct 模型启用 NextEdit 功能
- **状态**: 匹配范围已收缩至 `qwen3-coder`（原为 `qwen` 全品牌，过度泛化）
- **实现**:
  - `GenericFimNextEditProvider` 继承 `BaseNextEditModelProvider`
  - 使用 chat API + 结构化 system prompt（editable region 标记 + edit history + context）
  - `NextEditProviderFactory` fallback: 未知模型 → GenericFimNextEditProvider（不再 throw）
  - `autodetect.ts`: `MODEL_SUPPORTS_GENERIC_NEXT_EDIT = ["qwen3-coder"]`（仅已验证模型）
- **影响范围**: 不影响 Mercury/Instinct 已有路径
- **待验证**: 需实测 qwen3-coder 在 NextEdit 场景的准确率和稳定性

### P3: 多点相似编辑检测 (#21) ⚠️ 实验功能

- **文件**: `prediction/SimilarEditDetector.ts`, `CompletionProvider.ts`
- **功能**: 检测用户重复的结构化编辑模式，找到其他需要相同编辑的位置，预填充缓存
- **状态**: 默认关闭，需通过 `experimental_enableSimilarEditDetection: true` 启用
- **实现**:
  - `SimilarEditDetector` 类: 跟踪最近 20 次编辑
  - **模式提取**: 将代码转为结构骨架（关键字+标点保留，标识符替换为 `ID`），匹配结构相同的编辑
  - **位置查找**: 在当前文件中搜索结构匹配的其他行（仅单文件）
  - **编辑预测**: 基于标识符替换规则，从已有编辑推导新位置的补全
  - 现在允许 identical completion（最常见的批量编辑场景），去重由缓存系统处理
  - 结果存入 `AutocompleteLruCache`
- **集成**: `CompletionProvider.accept()` 触发（仅当 flag 启用时）
- **局限**: 仅搜索当前文件，不跨文件；标识符替换规则为启发式，存在误判风险
- **待验证**: 需要统计 false positive 率和实际命中率

## ⚠️ 已完成优化 (2026-03-24 第二批) — 缓存/质量/NextEdit（待验证）

### 缓存检查提前 (Fast-Path Cache)

- **文件**: `CompletionProvider.ts`
- **问题**: 缓存查询在 context collection + prompt build 之后（200-1600ms），cache hit 时全部浪费
- **修复**: 缓存检查移到 `shouldPrefilter()` 之后、context collection 之前
- **实现**: cache hit 时直接构建 outcome 返回，跳过 snippet 收集 + prompt 构建
- **预期**: cache hit 跳过 context collection + prompt build，延迟应显著降低（未精确测量）

### Temperature=0 + 配置覆盖

- **文件**: `CompletionProvider.ts`
- **问题**: 默认 temperature=0.01 引入微小随机性，降低缓存命中率
- **修复**: 默认值改为 0（确定性输出），用户可通过 config `completionOptions.temperature` 覆盖

### 补全与 Suffix 去重 (trimSuffixOverlap)

- **文件**: `postprocessing/index.ts`
- **问题**: 模型有时重新生成光标后已有的代码，导致插入时出现重复文本
- **修复**: 新增 `trimSuffixOverlap()`:
  1. 字符级检测: 找到补全尾部与 suffix 头部的最长精确重叠并截掉
  2. 行级检测: 补全末尾 N 行的 trim 内容与 suffix 前 N 行匹配则截掉
- **安全性**: 只在精确匹配时截断，不会误删有效补全

### 行级正则边界 Snippet 截断 (truncateAtBlockBoundary)

- **文件**: `templating/filtering.ts`
- **问题**: snippet 超出 token 预算时按行截断，可能截在函数/类体中间，降低模型理解
- **修复**: 新增 `truncateAtBlockBoundary()`:
  - 基于**行级正则**匹配代码块边界（`function`/`class`/`export`/`def`/`}`等），**非 tree-sitter AST**
  - 在最后一个完整代码块边界处截断
  - fallback: 若未找到边界则退化为按行截断
- **集成**: snippet 超出 per-key 或总体 token 预算时自动触发（不再跳过）

## Prompt 效率分析 (2026-03-24)

### 优化前 Prompt 结构

对于 qwen3-coder，优化前的 prompt 格式：

```
<|fim_prefix|>{formatted_snippets}\n{prunedPrefix}<|fim_suffix|>{prunedSuffix}<|fim_middle|>
```

其中 `formatted_snippets` 每个 snippet 被注释包裹：

```
// Path: utils/helpers.ts
// function formatDate(date: Date) {
//   return date.toISOString();
// }
```

### 优化后 Prompt 结构 (qwenCoderMultifileFimTemplate)

```
<|fim_prefix|><|repo_name|>myproject
<|file_sep|>src/utils.ts
function formatDate(date: Date) {
  return date.toISOString();
}
<|file_sep|>src/main.ts
import { formatDate } from './utils';
function main() {
  const d = <|fim_suffix|>  console.log(d);
}<|fim_middle|>
```

### Token 预算分配 (maxPromptTokens=8192)

| 组件                     | Token 数   | 占比     |
| ------------------------ | ---------- | -------- |
| prunedPrefix             | ~3,686     | 45%      |
| prunedSuffix             | ~2,048     | 25%      |
| 模板标记 (`<\|fim_*\|>`) | ~25        | <1%      |
| **可用于 snippets**      | **~2,433** | **~30%** |

### 发现的效率问题

#### 问题 1: Comment 包裹浪费 30-40% snippet token（严重）

每个 snippet 的每一行都被 `// ` 注释包裹（`commentifySnippet()`）：

- 100 行 snippet → +100 token 纯 `// ` 标记开销
- 5 个 snippet × 150 行 = +750 token 浪费
- **占 snippet 预算的 ~31%**

#### 问题 2: 未使用 qwen3-coder 原生多文件能力（严重）

qwen3-coder 原生支持：

```
<|repo_name|>my-project
<|file_sep|>src/utils.ts
function formatDate(date: Date) { ... }
<|file_sep|>src/main.ts
<|fim_prefix|>...
```

当前未使用 `<|repo_name|>` 和 `<|file_sep|>`，用注释包裹替代，浪费且降低模型理解能力。

#### 问题 3: base snippets 随机 shuffle（高）

`filtering.ts` 中 `shuffleArray()` 随机打乱 base snippets（import 定义 + root path 上下文），丧失相关性排序。对 sglang prefix caching 也不友好。

## ✅ 已完成优化 (2026-03-24 第三批) — 性能/质量改进

> 基于 Opus 4.6 × GPT 5.4 联合对话共识（`conversation_results.md`）实施。

### P0: RecentlyVisitedRangesService readFile → document.getText(range)

- **文件**: `extensions/vscode/src/autocomplete/RecentlyVisitedRangesService.ts`
- **问题**: 每次光标切换触发 `this.ide.readFile(filepath)` 读取整个文件 → `split("\n")` → `slice(start, end)` 取片段。对大文件产生不必要的全量磁盘 IO + 内存分配。
- **修复**: 替换为 `event.textEditor.document.getText(new vscode.Range(...))`:
  - 直接从 VS Code 内存中的 `TextDocument` 按行范围读取，零磁盘 IO
  - 无需全文 split + slice，减少内存分配
  - 兼容 VS Code 1.70.0+（`TextDocument.getText(range)` 自 API v1.0 起存在）
- **附加改动**: snippet 返回值新增 `startLine`/`endLine` 字段，用于下游 overlap-aware dedup
- **预期**: 大文件场景（>5000行）单次调用节省 5-20ms IO + GC

### P1: Snippet 类型扩展 — 行范围元数据

- **文件**: `snippets/types.ts`, `snippets/getAllSnippets.ts`
- **问题**: `AutocompleteCodeSnippet` 不携带行范围信息，无法做精确的 overlap 判断
- **修复**:
  - `types.ts`: `AutocompleteCodeSnippet` 新增可选字段 `startLine?: number`, `endLine?: number`
  - `getAllSnippets.ts`: `getSnippetsFromRecentlyEditedRanges()` 传播 `range.range.start.line` / `range.range.end.line`
- **影响**: 向后兼容（可选字段），仅在有行范围数据时启用 overlap-aware dedup

### P1: Base Token Floor — 15% 预留保底

- **文件**: `templating/filtering.ts`
- **问题**: editedRanges + visitedRanges + openedFiles 按优先级消耗预算后，base snippets（import 定义、root path 上下文、AST 结构）可能被完全饿死。base 提供的语法/类型信息对补全质量至关重要。
- **修复**:
  - 新增 `BASE_FLOOR_RATIO = 0.15`，计算 `baseFloor = Math.floor(totalSnippetBudget * 0.15)`
  - 非 base 类型的有效预算 = `remainingTokenCount - baseFloor`（为 base 保留最低 15%）
  - base 类型使用 `remainingTokenCount` 全额预算（可以用完剩余所有 token）
  - openedFiles 的 `formatOpenedFilesContext` 也使用 effectiveBudget 限制
- **预期**: maxPromptTokens=4096 时，base 至少获得 ~90 token（足以放入 1-2 个 import 定义签名）

### P1: Overlap-Aware Dedup — editedRanges 与 visitedRanges 去重

- **文件**: `templating/filtering.ts`
- **问题**: 已有的 editedRanges+visitedRanges 同文件互补机制对 editedRangesFilepaths 的文件放行 visitedRanges，但未检查内容是否重叠。若编辑范围与光标范围大幅重叠，会注入冗余内容浪费 token。
- **修复**:
  - 新增 `lineRangeOverlap(startA, endA, ranges)` 辅助函数，计算行范围重叠率（0.0-1.0）
  - 新增 `editedLineRanges` Map 追踪 editedRanges 已添加的每文件行范围
  - visitedRanges 过滤: 同文件 snippet 若与 editedRanges 行重叠 ≥ 50% → 跳过（避免重复）
  - editedRanges 处理时记录 `{ start, end }` 到 `editedLineRanges`
- **安全性**: 无行范围数据时默认放行（向后兼容），仅在有精确行号且重叠超阈值时过滤

### P2: countTokens 请求级缓存

- **文件**: `templating/filtering.ts`
- **问题**: `getSnippets()` 主循环中对 snippet 内容反复调用 `countTokens()`（首次计算 + 截断后计算 + 全局预算检查 = 同一内容 3-5 次）。`countTokens` 内部 tokenizer 调用开销 2-5ms/次，合计浪费 30ms+。
- **修复**:
  - `getSnippets()` 内新建请求级 `tokenCountCache = new Map<string, number>()`
  - 包装 `cachedCountTokens(content, modelName)`: key = `content::modelName`，命中返回缓存值
  - 替换主循环中所有 4 处直接 `countTokens()` 调用为 `cachedCountTokens()`
  - `truncateAtBlockBoundary()` 签名新增可选 `countFn` 参数（默认为原始 `countTokens`），两处调用点传入 `cachedCountTokens`
- **预期**: snippet 数量 ≥ 5 时节省 ~20-30ms（消除重复 tokenizer 调用）
- **生命周期**: 缓存随 `getSnippets()` 调用结束自动释放，无内存泄漏风险

### P2: HelperVars AST 缓存

- **文件**: `util/ast.ts`
- **问题**: `getAst()` 每次调用都创建新 Parser 并重新 parse 整个文件内容，即使文件内容未变（连续打字触发的多次补全请求对同一文件反复 parse）。
- **修复**:
  - 模块级 `astCache = Map<filepath, { content, tree }>` 缓存已解析的 AST
  - 命中条件: filepath 相同且 content 字符串严格相等
  - LRU 淘汰策略: 超过 `MAX_AST_CACHE_SIZE=20` 时删除最早插入的条目
  - 未命中时正常 parse 并写入缓存
- **预期**: 连续编辑同一文件时，跳过 tree-sitter parse (~5-15ms/次)，仅首次 parse
- **安全性**: Map 引用计数管理，删除条目后 Tree 被 GC 回收

### P2: autocomplete maxTokens=256

- **文件**: `templating/index.ts`
- **问题**: LLM 默认 `maxTokens=4096`（`DEFAULT_MAX_TOKENS`），但 autocomplete 补全通常只需 50-150 tokens。过大的 maxTokens 导致:
  1. sglang 为每个请求预分配 4096 token 的 KV cache 槽位，浪费 GPU 显存
  2. `pruneLength()` 按 4096 预留生成空间，压缩了 prompt 可用预算
- **修复**:
  - 新增 `AUTOCOMPLETE_MAX_TOKENS = 256` 常量
  - `renderPrompt()` 和 `renderPromptWithTokenLimit()` 返回的 `completionOptions` 中设置 `maxTokens: 256`（模板/用户配置可覆盖，因 spread 在后）
  - `pruneLength()` 改用 `AUTOCOMPLETE_MAX_TOKENS` 作为默认预留值（替代 `DEFAULT_MAX_TOKENS`）
- **预期**:
  - sglang KV cache 预分配减少 ~93%（4096→256），提升并发吞吐
  - prompt 可用预算增加 ~3840 tokens（对大 contextLength 模型影响不大，但对小 contextLength 模型有帮助）
- **兼容性**: 用户可通过 `completionOptions.maxTokens` 覆盖；模板级 completionOptions 也可覆盖

  - 可能原因: LRU cache `max=5` 文件，如果访问其他文件后 config.json 被驱逐
  - `onDidChangeTextEditorSelection` 需要用户实际点击文件（不只是预览）才会缓存
- **修复**: 添加诊断日志
  - `[Autocomplete SnippetCounts]`: 各来源 snippet 数量 + visited 文件名列表
  - `[Autocomplete FilterResult]`: 最终进入 prompt 的 snippet 数量和来源
- **文件**: `getAllSnippets.ts`, `filtering.ts`

#### Issue 4: 注释格式从编程语言注释改为结构化标注

- **问题**: 原先 `// #recent edit`、`// #definition` 等注释容易与编程语言注释混淆
- **修复**: 改为结构化 bracket 格式 `[PROMPT: SOURCE_TYPE - PRIORITY_LEVEL PRIORITY]`
  - `[PROMPT: RECENT_EDIT - HIGH PRIORITY]` (editedRanges, 优先级 1)
  - `[PROMPT: CURSOR_CONTEXT - HIGH PRIORITY]` (visitedRanges, 优先级 2)
  - `[PROMPT: OPEN_FILE - MEDIUM PRIORITY]` (openedFiles, 优先级 3)
  - `[PROMPT: GIT_DIFF - LOW PRIORITY]` (diff, 优先级 98)
  - `[PROMPT: DEFINITION - LOW PRIORITY]` (base/importDef/rootPath, 优先级 99)
- **优点**: 语言无关、不与任何语言注释语法冲突、优先级信息对模型理解上下文结构有帮助
- **文件**: `filtering.ts`

### 2026-03-27 (生产日志分析修复 Batch 5)

基于 2026-03-26 构建的 `continue-win32-x64-1.3.19.vsix` 实际生产环境测试日志分析。

#### Issue 1: output:exthost 污染 prompt

- **根因**: VS Code Extension Host 的输出面板 (`output:exthost`) 被 `RecentlyVisitedRangesService` 捕获为"已访问范围"，将内部日志文本注入到自动补全 prompt 中
- **影响**: 每次请求注入相同的垃圾上下文 → prompt 内容相似 → temperature=0 下产生重复补全
- **原有过滤**: 仅屏蔽 `output:extension-output-Continue.continue`（Continue 自身的输出面板）
- **修复**: 将过滤条件从精确匹配改为前缀匹配 `!s.filepath.startsWith("output:")`，屏蔽所有 output scheme URI（exthost、debug console、其他扩展输出等）
- **文件**: `extensions/vscode/src/autocomplete/RecentlyVisitedRangesService.ts`

#### Issue 2: HelperVars.init() 耗时 1600-1700ms (double readFile)

- **根因**: `HelperVars.init()` 通过 `ide.readFile()` 读取文件内容后，调用 `constructInitialPrefixSuffix(this.input, this.ide)` 时又在内部重复执行了一次 `ide.readFile()` IPC 调用
- **分析**: `constructInitialPrefixSuffix` 检查 `input.manuallyPassFileContents`，但 HelperVars 未设置该字段
- **修复**: 在 readFile 后设置 `this.input.manuallyPassFileContents = this._fileContents`，使 `constructInitialPrefixSuffix` 直接复用已读取的内容，消除冗余 IPC
- **文件**: `core/autocomplete/util/HelperVars.ts`

#### Issue 3: HelperVars.init() 缺少内部子计时

- **问题**: Batch 4 的 sub-timing 仅分解到 `helperVarsMs` 级别，无法定位 init() 内部的具体瓶颈
- **修复**: 在 init() 中添加 5 段子计时: `workspaceDirsMs`(IPC)、`readFileMs`(IPC)、`constructPrefixSuffixMs`、`prunePrefixSuffixMs`(2×countTokens)、`astParseMs`(tree-sitter)
- **日志格式**: `[HelperVars SubTimings] workspaceDirsMs=X readFileMs=X constructPrefixSuffixMs=X prunePrefixSuffixMs=X astParseMs=X totalInitMs=X`
- **文件**: `core/autocomplete/util/HelperVars.ts`

#### 重复补全问题

- **分析**: 由 Issue 1 (output:exthost 污染) 导致。相同的垃圾上下文 + temperature=0 = 相同的输出
- **结论**: Issue 1 修复后，不同光标位置将产生不同的代码上下文，自然消除重复问题
