# PyCharm 自动补全 QueueManager 接入 (2026-04-07 ~ 04-10)

## 背景

VS Code 侧通过 `ContinueCompletionProvider` 创建独立的 `QueueManager`，事件驱动预收集 snippet。
PyCharm/IntelliJ 侧通过 `Core → CompletionProvider`，但 Core 创建 CompletionProvider 时**未传入 QueueManager**，
导致始终走 legacy path（on-demand 收集），totalContextMs 390-472ms。

## 根因分析

| #   | 根因                                                                            | 影响                  |
| --- | ------------------------------------------------------------------------------- | --------------------- |
| 1   | `core.ts` 创建 CompletionProvider 时只传 5 参数，缺少第 6 参数 QueueManager     | 永远走 legacy path    |
| 2   | `shouldPrefilter()` 重复调用 `getWorkspaceDirs()` + `readFile(.continueignore)` | prefilterMs 107-140ms |
| 3   | `HelperVars.create()` 外部计时 vs 内部计时有 ~150ms 差距                        | 需诊断                |

## 实施方案

### Phase 1: Core.ts QueueManager 接入

**文件**: `core/core.ts`

1. Import `QueueManager` from `./autocomplete/context/QueueManager`
2. 在 Core 类中新增 `private queueManager: QueueManager` 属性
3. 构造时 `this.queueManager = new QueueManager()` 并传入 CompletionProvider 第 6 参数

### Phase 1.2: 事件接线

**文件**: `core/core.ts`

在 `files/opened` handler 中：

- 读取文件前 30 行 header 内容
- `queueManager.pushOpenedFile()` 推入 openedFilesQueue
- `queueManager.markCoreReady()` 标记同步队列可用
- `queueManager.startWarming()` + `completionProvider.warmFile()` 异步预热 import

在 `files/closed` handler 中：

- `queueManager.removeOpenedFile()` 清理已关闭文件

### Phase 1.3: 回填逻辑

**文件**: `core/autocomplete/CompletionProvider.ts`

当 legacy path 执行后，将收集到的 openedFileSnippets 和 importDefinitionSnippets 回填到 QueueManager，
标记 core-ready + full-ready，使后续请求走 fast path。

### Phase 2: Prefilter IPC 缓存

**文件**: `core/autocomplete/prefiltering/index.ts`

1. 模块级缓存 `_cachedWorkspaceIgArray`（TTL 30s）避免每次请求读取 `.continueignore`
2. `isDisabledForFile()` 改为同步，直接接收 `workspaceDirs` 参数（来自 `helper.workspaceUris`），不再重复 IPC
3. 预期节省 prefilterMs ~100ms

### Phase 3: HelperVars 诊断计时

**文件**: `core/autocomplete/util/HelperVars.ts`

在 `create()` 中添加 `Date.now()` 打点，输出 `create() total=Xms`，
与已有的 `[HelperVars SubTimings]` 配合，定位外部-内部计时差距来源。

## 安全分析

- VS Code 不通过 Core 发送 `autocomplete/complete` → Core 的 CompletionProvider + QueueManager 对 VS Code 侧无影响
- QueueManager 是实例级对象，不干扰 VS Code 侧独立的 QueueManager 实例
- 未就绪时 fallback 到 legacy path → 零退化风险
- IntelliJ 已发送 `files/opened`/`files/closed`/`files/changed` 事件 → 无需 Kotlin 改动

## 统一事件处理实现 (Phase 1.4)

### 架构说明

VSCode 和 IntelliJ 采用不同的架构：

- **VSCode**: 单进程架构，拥有独立的 `ContinueCompletionProvider` 和 `QueueManager`
- **IntelliJ**: 多进程架构，IDE 进程 + Core 进程，通过 IPC 通信

为了使 IntelliJ 也能利用 QueueManager 的预收集能力，在 Core.ts 中添加了统一的事件处理：

### Core.ts 事件处理

```typescript
// files/smallEdit - 编辑事件
on("files/smallEdit", async ({ data }) => {
  if (data.actions && data.actions.length > 0) {
    for (const action of data.actions) {
      if (action.filepath && action.editText) {
        this.queueManager.pushEdited(
          action.filepath,
          content,
          paddedStart,
          paddedEnd,
        );
      }
    }
  }
});

// files/cursorMoved - 光标移动事件
on("files/cursorMoved", async ({ data }) => {
  this.queueManager.pushVisited(
    data.filepath,
    data.content,
    data.startLine,
    data.endLine,
  );
});
```

### IntelliJ 端事件发送

**DocumentChangeTracker.kt** - 发送编辑事件：

```kotlin
private fun sendEditEventToCore(event: DocumentEvent) {
    val editAction = mapOf(
        "filepath" to filepath,
        "range" to mapOf(...),
        "fileContents" to fileContents,
        "editText" to event.newFragment.toString(),
        ...
    )
    coreMessenger?.request("files/smallEdit", mapOf(
        "actions" to listOf(editAction)
    ), null) { }
}
```

**ActiveHandlerManager.kt** - 发送光标移动事件：

```kotlin
private fun sendCursorMovedEventToCore(editor: Editor, position: LogicalPosition) {
    // 提取光标周围 ±30 行内容
    val content = document.getText(TextRange(startOffset, endOffset)).trim()
    coreMessenger?.request("files/cursorMoved", mapOf(
        "filepath" to filepath,
        "content" to content,
        "startLine" to startLine,
        "endLine" to endLine
    ), null) { }
}
```

### 性能优化点

1. **零 IO**: 内容直接从内存中的 document 对象提取，不涉及文件系统读取
2. **非阻塞**: 事件发送是异步的，不阻塞 UI 线程
3. **预收集**: 编辑和光标移动时预收集上下文，autocomplete 时直接使用队列中的数据

## 问题 1: 服务器端 abort 数量过多，影响性能

### 根因链

```
用户连续击键
  → debounce 定时器重置
  → 但前一个请求已通过 debounce，正在推理后端流式推理（本次样本环境为 sglang）
  → GeneratorReuseManager.getGenerator() 发现 prefix 不匹配
  → ListenableGenerator.cancel() 触发 AbortController.abort()
  → fetch 侧中止请求 / 关闭客户端流
  → 已开始的 prefill / decode 白做 → KV cache 占用直到后端完成清理
```

### 代码路径

| 步骤                      | 文件                       | 位置 | 说明                                                                 |
| ------------------------- | -------------------------- | ---- | -------------------------------------------------------------------- |
| 1. 创建主 AbortController | `CompletionProvider.ts`    | L237 | 存入 `_abortControllers` Map                                         |
| 2. 创建副 AbortController | `GeneratorReuseManager.ts` | L49  | 包装到 ListenableGenerator                                           |
| 3. prefix 不匹配触发取消  | `GeneratorReuseManager.ts` | L49  | `_createListenableGenerator()` 中取消旧 generator                    |
| 4. abort 传播到 fetch     | `llm/index.ts`             | L507 | `fetch()` 的 catch 记录第一条 error (`llm_fetch`)                    |
| 5. 错误冒泡再次被捕获     | `llm/index.ts`             | L813 | `streamComplete()` 的 catch 记录第二条 error (`llm_stream_complete`) |

### 影响量化

每次 abort：

- 浪费推理后端 GPU 推理（prefill + 已生成 decode 步）
- 占用推理后端 KV cache slot（8K token prompt ≈ 几十 MB 显存）直至清理
- 产生 **2 条 error 日志**（`llm_fetch` + `llm_stream_complete`）——同一个 AbortError 在 `llm/index.ts` 的两层 catch 中各被捕获一次
- 网络往返开销（TCP 建连 + RST）

### 更深一层的根因（架构级）

如果只把问题归因成「debounce 太小」或「取消不够快」，还是停留在现象层。更根上的问题是：

**当前 autocomplete 控制链没有一个显式的“请求准入 / 生命周期协调层”。**

现在的职责分散在多个点：

- `CompletionProvider.ts` 负责 editor event 入口、debounce、上下文收集和发起生成
- `GeneratorReuseManager.ts` 负责 generator 复用与取消旧 generator
- `CompletionStreamer.ts` 负责流式过滤与 full stop
- `llm/index.ts` 负责 fetch / streamComplete 的底层取消

但这几层之间没有一个统一状态机去回答下面这些关键问题：

1. 当前请求是否只是“候选请求”，还是已经被允许占用模型资源？
2. 同一文档 / 同一模型当前是否已经有 in-flight 生成？
3. 新请求到来时，应当直接替换旧请求、等待旧请求、复用旧请求，还是只更新最新快照？
4. 旧请求是在首 token 前被取消，还是已经进入有效流式阶段后才被取消？

结果就是：**abort 被当成主要控制手段，而不是调度层的例外收尾动作。**

这才是 abort 率偏高的架构级根因。动态 debounce 下限过低，只是在这个架构缺口上继续放大了重叠请求。

### 修复方案

**方案 A (P0): 降低 abort 日志级别**

文件: `core/llm/index.ts` L507 (`fetch()` 方法) 和 L813 (`streamComplete()` 方法)

```typescript
// 当前: Logger.error(e, { context: "llm_fetch", ... });
// 改为:
if (isAbortError(e)) {
  Logger.debug("Autocomplete request aborted", { context: "llm_fetch", ... });
} else {
  Logger.error(e, { context: "llm_fetch", ... });
}
```

同理修改 `streamComplete()` 的 catch (L813)。双日志的根因是同一个 AbortError 在调用链冒泡时被两层 catch 各捕获一次，两处都需要降级。

**方案 B (P1): 修复 debounce pause bucket 下限**

不引入额外的生命周期协调层。abort 机制本身是正确的——它保证用户真实请求立即独占资源。问题在于伪请求不该被放出去——这是 debounce 的责任。

pause bucket 的 bug：停顿后的首键（interval > 200ms）被映射到 30ms 延迟，但停顿后首键几乎永远不是完整意图：

```
用户停顿 500ms → 开始打 "return" (6个字符)
  "r" 到达: interval > 200ms → pause bucket → 30ms → 请求 k1 发出！
  "e" 到达 60ms 后: interval < 80ms → fast bucket → 200ms → debounce 住了
  ...后续字符都被 debounce 住
  最终 "n" 之后无新字符 → 请求 k6 发出（真正有价值的）
```

k1 在 30ms 就被放出去，60ms 后 "e" 到达时它已经在飞。这个 k1 100% 是废请求。

修复：`return 30` → `return Math.max(120, configDelay)`

120ms 的理由：

- 真实单字符编辑：120ms 后发请求，体感延迟 ~120ms+TTFT——可接受
- 连续打字（>12 chars/sec，interval <80ms）：第二键 ~60ms 到达，重置 debounce，k1 被拦住
- 中速打字（interval ~100ms）：第二键 ~100ms 到达，也能在 120ms 窗口内重置

这样 debounce 拦住绝大部分伪请求，偶尔漏网的由现有 abort 机制兜底。abort 从“主要控制手段”回归“例外收尾”，不需要任何新的协调层。

## 问题 2: 自动补全多数情况出不来，PyCharm 最常见

### PyCharm 特有根因 (相比 VS Code 额外的 4 个因素)

#### 2a. JetBrains 缺少 abort 信号传播 (最关键)

**文件**: `extensions/intellij/.../ContinueCompletionService.kt`

```kotlin
// 当前: 不传 AbortSignal，无法从 IDE 端取消 core 请求
coreMessenger?.request("autocomplete/complete", requestInput, null) { }
```

当 JetBrains 端 `withTimeoutOrNull(modelTimeout * 3)` 超时返回 null 后，core 端的 LLM 请求 **仍在运行**。下次击键触发新请求时，新旧请求会在推理后端并发竞争；本次日志样本里表现为 sglang 队列拥堵，但这个问题并不局限于 sglang。

**VS Code 对比**: `AbortController` 从 `CompletionProvider` 一路传到 `fetch(url, { signal })`，超时后清理干净。

#### 2b. 固定间隔 debouncer

**文件**: `extensions/intellij/.../Debouncer.kt`

```kotlin
// JetBrains: 简单固定延迟
fun debounce(action: suspend () -> Unit) {
    debounceJob?.cancel()
    debounceJob = coroutineScope.launch { delay(interval); action() }
}
```

**VS Code**: `AutocompleteDebouncer.ts` 有自适应延迟：

- 快速打字 (<80ms) → 150-200ms 延迟（合并请求）
- 正常打字 → 80ms
- 停顿 (>200ms) → 30ms（快速响应）

JetBrains 没有这种自适应能力，快速打字时发出更多无效请求。

但进一步看 VS Code 侧，这个自适应实现也不是没有问题：在 `AutocompleteDebouncer.ts` 中，停顿分支会**直接返回 30ms**，绕过 `debounceDelay` 的基准值；而在本次 VS Code 日志中，`debounceWaitMs` 大多数都落在 29-32ms，说明当前策略几乎长期停在这个最激进的快速路径。

结合日志中的另外两组事实：

- `totalContextMs` 在多数请求里仅 2-4ms，说明 debounce 后请求会非常快地推进到 LLM
- `streamMs` 常落在 500-3100ms，说明前一个请求往往仍在流式解码阶段

这意味着：**30ms 下限不是根因本身，而是会显著放大现有架构缺口上的重叠请求和 abort 率。**

更准确的定性应该是：

- JetBrains 的问题是“固定 debounce + 缺取消传播”
- VS Code 的问题是“已有 adaptive debounce，但 pause bucket 下限过低，且完全不感知在飞请求/最近流式延迟”

因此的修复策略是：**直接修复 VS Code 的 pause bucket 下限（P1-5），然后把 JetBrains Debouncer.kt 改为相同的自适应行为（P2-10）。** 不引入额外协调层，现有 abort 机制作为安全网兜底。

#### 2c. `mock:///` URI 导致上下文收集和路径展示异常

JetBrains 对虚拟文件返回 `mock:///` scheme，这是一个 **URI 规范化缺失** 的系统性问题，影响多个层面：

- `AutocompleteTemplate.ts` 中 `getFileName()` 只检查 `startsWith("file://")` → `mock:///` 原样写入 LLM prompt（如 `<|file_sep|>mock:///bpp_case_tools.py`）
- `core/util/uri.ts` 中 `findUriInDirs()` 做 scheme 匹配 → `mock:///` 与 `file://` workspace 不匹配 → 文件被跳过
- `core/util/filesystem.ts` 中 `fileURLToPath()` 对 `mock:///` 会抛异常（但不在 ImportDefinitionsService 直接调用链上）

修复落点在 **core 层**：在接收 IntelliJ 发送的内容后，core 自己负责把 `mock:///` URI 规范化为 `file://`。不修改 IntelliJ 侧行为，保持兼容性：

- 在 `core/util/uri.ts` 或请求入口层统一做 URI scheme 规范化
- 对 `mock:///path` 提取路径部分，重组为 `file:///path`
- 对其他非标准 scheme 同理处理，保证下游的 `getFileName()`、`findUriInDirs()` 正常工作

#### 2d. 文档仅 ±5 行增量同步

**文件**: `extensions/intellij/.../DocumentChangeTracker.kt`

```kotlin
val paddedStart = Math.max(0, startLine - 5)
val paddedEnd = Math.min(document.lineCount - 1, endLine + 5)
```

core 可能持有过期文件内容。

### 通用根因 (VS Code 也存在)

#### 2e. `noDoubleNewLine()` 过滤器杀死补全

**文件**: `core/autocomplete/filtering/streamTransforms/lineStream.ts` L664

```typescript
export async function* noDoubleNewLine(lines: LineStream): LineStream {
  let isFirstLine = true;
  for await (const line of lines) {
    if (line.trim() === "" && !isFirstLine) {
      return; // ← 见到空行就终止整个 pipeline！
    }
    isFirstLine = false;
    yield line;
  }
}
```

Python 中语句间常有空行 (PEP 8 风格)。LLM 输出: `line1 + \n + \n + line2` → 经过该过滤器后只剩 `line1`（可能只有一个换行符或空白） → rawLen=1 → `PostReject reason=isBlank`。

这是日志中大量 `rawLen=0` / `rawLen=1` + `PostReject isBlank` 的 **主要来源**。

#### 2f. 推理后端 prefill 延迟 vs showWhatever 超时竞争

prompt 长度 ~8000 tokens 时，vLLM / sglang 这类推理后端的 prefill 都可能达到 200-500ms。`showWhateverWeHaveAtXMs()` 存在双重问题：(a) 从 pipeline **开始**计时（含 prefill 等待），(b) `StreamTransformPipeline.ts` L75 传入的值是 `modelTimeout` 而非专用展示超时。如果 prefill 期间没有 token 到达，实际留给 decode 的窗口极短或为零。

### 修复方案

**方案 A (P0): 修复 `noDoubleNewLine()`**

改为 **允许单个空行**，仅在连续双空行时停止：

```typescript
export async function* noDoubleNewLine(lines: LineStream): LineStream {
  let isFirstLine = true;
  let lastLineWasEmpty = false;

  for await (const line of lines) {
    const isEmpty = line.trim() === "";
    if (isEmpty && lastLineWasEmpty && !isFirstLine) {
      return; // 连续两个空行才停止
    }
    if (isEmpty && !isFirstLine) {
      lastLineWasEmpty = true;
      yield line;
      continue;
    }
    lastLineWasEmpty = false;
    isFirstLine = false;
    yield line;
  }
}
```

**~~方案 B (P1): PyCharm 增加 abort 信号传播~~ 暂不做**

**方案 C (P2): JetBrains Debouncer.kt 改为与 VS Code 相同的自适应行为**

直接将 JetBrains 的固定间隔 `Debouncer.kt` 改为与 VS Code `AutocompleteDebouncer.ts` 相同的 3-bucket 自适应策略（含 120ms pause bucket 修复）。不引入协调层。

## 问题 3: 自动补全出半截（语句不完整）

### 根因 1 (主要): `showWhateverWeHaveAtXMs()` 超时截断 — 双重问题

**文件**: `core/autocomplete/filtering/streamTransforms/lineStream.ts` L643

```typescript
export async function* showWhateverWeHaveAtXMs(
  lines: LineStream,
  ms: number,
): LineStream {
  const startTime = Date.now(); // ← 计时从 pipeline 开始！
  let firstNonWhitespaceLineYielded = false;

  for await (const line of lines) {
    yield line;
    if (!firstNonWhitespaceLineYielded && line.trim() !== "") {
      firstNonWhitespaceLineYielded = true;
    }
    const isTakingTooLong = Date.now() - startTime > ms;
    if (isTakingTooLong && firstNonWhitespaceLineYielded) {
      break; // ← 超时截断
    }
  }
}
```

**问题 A**: `startTime` 在 pipeline 开始计时，包含了推理后端 prefill 等待时间。对于 8000 token prompt，在 vLLM / sglang 上 prefill 可能 200-400ms。如果 `modelTimeout=300ms`，实际留给 decode 生成的窗口只有 0-100ms。

**问题 B (更关键)**: `StreamTransformPipeline.ts` L75 传入的超时值是 `modelTimeout`，而非专用的展示超时配置：

```typescript
const timeoutValue = helper.options.modelTimeout; // L75 — 用了 modelTimeout!
// ...
showWhateverWeHaveAtXMs(lineGenerator, timeoutValue!); // L77
```

也就是说，不仅计时起点过早，使用的超时值本身也不合适——`modelTimeout` 通常比合理的 "展示已有内容" 超时更短。

**日志证据**: PyCharm 第一个请求生成 `if response.status_code != 20` (38 chars, 缺 `0:`)，streamMs=2440ms（使用了另一个模型 Qwen3-Coder-Next-AWQ-8bit）。

### 根因 2: `noDoubleNewLine()` 空行截断

LLM 输出两行代码中间有空行 → 第一行之后的空行触发 return → 只显示第一行。

### 根因 3: Stop token 意外命中

当前 stop tokens 包含 `/src/`、`#- coding: utf-8`、` ``` `。如果 Python 代码中出现文件路径包含 `/src/`，会意外截断。

### 修复方案

**方案 A (P0): 修改计时起点 + 使用独立超时配置**

1. 将 `startTime` 延迟到首 token 到达：

```typescript
export async function* showWhateverWeHaveAtXMs(
  lines: LineStream,
  ms: number,
): LineStream {
  let startTime: number | null = null; // ← 延迟到首 token
  let firstNonWhitespaceLineYielded = false;

  for await (const line of lines) {
    if (startTime === null) {
      startTime = Date.now(); // ← 从 LLM 首 token 到达开始计时
    }
    yield line;
    if (!firstNonWhitespaceLineYielded && line.trim() !== "") {
      firstNonWhitespaceLineYielded = true;
    }
    const isTakingTooLong = Date.now() - startTime > ms;
    if (isTakingTooLong && firstNonWhitespaceLineYielded) {
      break;
    }
  }
}
```

2. 在 `StreamTransformPipeline.ts` 中将超时值从 `modelTimeout` 改为独立配置：

```typescript
// 当前 (L75):
const timeoutValue = helper.options.modelTimeout;
// 改为:
const timeoutValue =
  helper.options.showWhateverTimeout ?? helper.options.modelTimeout;
```

**方案 B (P1): 审查 `/src/` stop token**

`/src/` 可能在 Python 文件路径中出现（如 `from src.utils import ...`），考虑移除或改为仅在行首匹配。

## 问题 4: 单行补全多、多行补全少

### 根本原因: `noDoubleNewLine()` 过滤器

Python 代码风格要求函数体内语句间有空行 (PEP 8)。LLM 生成的多行代码几乎必然包含空行：


`noDoubleNewLine()` 见到空行就 `return` → 只允许第一行通过。

### 次要原因: `shouldCompleteMultiline()` 分类器

**文件**: `core/autocomplete/classification/shouldCompleteMultiline.ts`

- 如果在单行注释 `//` 内 → 强制单行
- 如果 IntelliSense 补全项被选中 → 强制单行
- 语言特定规则可能限制多行

### 修复方案

同上问题 2 方案 A — 修改 `noDoubleNewLine()` 允许单个空行。这是解决单行/多行比例失调的 **核心修复**。

## 问题 6: Prompt 中缺少调用函数的签名/入参/返回值

### 根本原因: ImportDefinitionsService 在当前环境基本不工作

日志中始终 `import=0(0t)`。

### 最直接根因: cache miss 无同步兜底

autocomplete 取 import snippets 时优先读 cache；如果 cache miss，直接返回空结果。`ImportDefinitionsService` 在 `onDidChangeActiveTextEditor` 时异步填充 cache，但如果异步填充失败（gotoDefinition 超时、binary IPC 延迟等），cache 就始终为空。

### 底层失败链路（解释为什么 cache 始终为空）

```
ImportDefinitionsService._getFileInfo()
  → tree-sitter parse (需要 import-queries/python.scm)
  → 如缺失 → return { imports: {} }

  → query.matches() 提取 import 符号
  → ide.gotoDefinition() 解析每个符号
    → binary 模式走 IPC → 延迟高 → 150ms 超时后返回空

  → cache.get() 返回 undefined (异步预热未完成或已失败)

外层:
  → getAllSnippetsWithoutRace() 中
  → racePromise(contextRetrievalService.getSnippetsFromImportDefinitions(helper), 200)
  → 整个 import 解析超过 200ms → 全部丢弃返回空数组
```

### 设计局限

即使 ImportDefinitionsService 完全正常工作，它也**仅覆盖**：

- import 语句中声明的符号

**不覆盖** (当前完全缺失)：

- 当前函数体中调用的其他函数的签名
- 局部/内置函数的定义
- 返回值类型信息
- 参数说明和 docstring
- 类方法的 self 引用

### 修复方案（修订：DefinitionCacheService 统一方案）

不再沿用原 ImportDefinitionsService 的 cache miss 兜底思路。原方案仅覆盖 import 符号，且依赖 tree-sitter import-queries 语法文件和 gotoDefinition IPC（延迟高、超时严）。

**新方案 (P1-7/8): 创建 DefinitionCacheService —— 项目内调用函数定义内存缓存**

目标：为补全 prefix 和 suffix 中出现的**项目内函数调用**提供函数声明、参数、文档说明作为 prompt 上下文。

设计要点：

1. **内存缓存**：`Map<functionName, DefinitionEntry>`，DefinitionEntry 包含函数签名行 + 参数列表 + docstring 首段
2. **缓存来源（优先级）**：
   - 优先从 IDE 解析结果抽取（`ide.gotoDefinition()` → 读定义处几行代码）
   - IDE 超时/不可用时，自行解析：从已知的 openedFiles / recentlyEditedFiles 中用简单正则或 tree-sitter 匹配函数定义
3. **触发时机**：
   - 异步预热：文件打开/编辑时，扫描 import + 函数定义，填充缓存
   - 同步兜底：autocomplete 请求时，从 prefix/suffix 提取调用函数名列表，对 cache miss 的条目尝试快速解析（带 300ms 超时）
4. **覆盖范围**（相比旧 ImportDefinitionsService 的扩展）：
   - ✅ import 语句引入的函数
   - ✅ prefix/suffix 中调用的项目内函数（非标准库）
   - ✅ 类方法（`self.method()` / `this.method()`）
   - ✅ 函数签名 + 参数 + docstring/JSDoc 首段
5. **Token 预算**：复用现有 `import` snippet 的 priority 和 token 预算分配

```typescript
// 伪代码示意
class DefinitionCacheService {
  private cache = new Map<string, DefinitionEntry>();

  // 异步预热：文件打开/编辑时
  async warmFile(filepath: string, content: string): Promise<void> { ... }

  // 同步获取：autocomplete 时从 prefix/suffix 提取调用名，查缓存
  async getDefinitionsForContext(
    callNames: string[],
    ide: IDE,
    timeoutMs: number = 300,
  ): Promise<AutocompleteSnippet[]> {
    const results: AutocompleteSnippet[] = [];
    for (const name of callNames) {
      let entry = this.cache.get(name);
      if (!entry) {
        // cache miss: 尝试 IDE gotoDefinition 或自行 parse
        entry = await this.resolveDefinition(name, ide, timeoutMs);
        if (entry) this.cache.set(name, entry);
      }
      if (entry) results.push(entry.toSnippet());
    }
    return results;
  }
}
```

## 2026-04-10 优化

### 已完成：LLM 阶段 latest-only (epoch 控制)

**文件**: `core/autocomplete/generation/CompletionStreamer.ts`

**问题**: `provideInlineCompletionItems` 是异步可重入的，每次按键都进入。debounce 在函数内部，不阻拦入口。
多个请求并发跑完 HelperVars → snippet → prompt → **LLM stream**，LLM stream 是最贵的阶段。

**方案选择**:

- ❌ CompletionProvider 入口代际控制 — 能覆盖全链路，但改动大，需合并外部 token
- ❌ GeneratorReuseManager 内做控制 — 它管的是 generator 复用不是请求生命周期，看不到外部 token
- ✅ CompletionStreamer epoch 控制 — 只管最贵的 LLM 阶段，改动最小，性价比最高

**实现**:

- 新增 `_latestStreamEpoch: number` 字段
- 每次进入 `streamCompletionWithFilters` 时 `epoch++`，记为 `myEpoch`
- 定义 `isStale = () => myEpoch !== this._latestStreamEpoch`
- 两个检查点：
  1. `generatorWithCancellation` 消费循环：`token.aborted || isStale()` → `fullStop(); return`
  2. `transformedGenerator` 最终输出循环：`isStale()` → `fullStop(); return`
- 新请求到来时 epoch 自增，旧流在下次 yield 前发现过期并停止

**代价（已接受）**:

- debounce 前的 prepareLlm、HelperVars、snippet、prompt 阶段仍可能并发（通常 < 50ms）
- 不是严格全链路 latest-only，是 LLM 阶段 latest-only

**根因评估**: ✅ 解决多个 LLM stream 并发浪费的问题。零额外对象分配，零签名变更。

### 已完成：过滤系统 stdlib definition（datetime.py 等）

**文件**: `core/autocomplete/context/ImportDefinitionsService.ts`

**问题**: prompt 中出现 `datetime.py` 等 Python 标准库的 definition 内容。
原因是 `ImportDefinitionsService._getFileInfo()` 对 import 符号做 gotoDefinition 后，

**修改**:

**根因评估**: ✅ 根因修复。与 `DefinitionCacheService` 对齐过滤策略。

### 已完成：snippet 注释从结构化标记改为自然语言风格

**文件**: `core/autocomplete/templating/filtering.ts`

**问题**: prompt 中 snippet 标注使用 `[PROMPT: RECENT_EDIT - HIGH PRIORITY]` 格式，
这不是代码注释的自然写法，LLM 可能视为特殊指令而非上下文参考。

**修改前** (结构化标记):


**修改后** (自然注释风格):

```

```

**标签映射**:
| 原标签 | 新标签 |
|--------|--------|
| `[PROMPT: RECENT_EDIT - HIGH PRIORITY]` | `--- Reference: recently edited code ---` |

| `[PROMPT: OPEN_FILE - MEDIUM PRIORITY]` | `--- Reference: code from open file ---` |
| `[PROMPT: GIT_DIFF - LOW PRIORITY]` | `--- Reference: recent git changes ---` |
| `[PROMPT: DEFINITION - LOW PRIORITY]` | `--- Reference: related definition ---` |

**设计原则**: 伪装成开发者在代码中写的参考注释，让 LLM 自然地将其理解为上下文参考，
而非解析特殊指令。`---` 分隔线是多种语言中常见的注释分隔风格。

**根因评估**: ✅ 改善 prompt 质量。减少 LLM 对结构化标记的"解析倾向"，提高上下文利用效率。

### 已完成：Debounce 从动态自适应改为固定值（VS Code + IntelliJ 同步）

**文件**:

- `core/autocomplete/util/AutocompleteDebouncer.ts` (VS Code)
- `extensions/intellij/.../utils/Debouncer.kt` (IntelliJ)

**问题**: 原 3-bucket 自适应 debounce 逻辑复杂且行为不可预测：

- fast typing (<80ms) → 200ms
- normal typing (<200ms) → 80ms
- pause (≥200ms) → min(120, configDelay)

停顿后首键被映射到极短延迟（原为 30ms，后修为 120ms），但整个自适应机制在有了 LLM 阶段 latest-only epoch 控制后不再必要。

**修改前** (3-bucket 自适应):

```typescript
// VS Code: 跟踪 recentIntervals 滑动窗口，计算 median，分 3 个 bucket
private getAdaptiveDelay(configDelay: number): number {
  // ... 30+ 行 median 计算 + 分桶逻辑
  if (medianInterval < 80) return Math.min(configDelay, 200);
  else if (medianInterval < 200) return Math.min(configDelay, 80);
  else return Math.min(120, configDelay);
}
```

```kotlin
// IntelliJ: 相同的 3-bucket 逻辑
private fun getAdaptiveDelay(): Long {
  // ... median 计算 + 分桶
  return when {
    medianInterval < 80 -> minOf(configDelay, 200)
    medianInterval < 200 -> minOf(configDelay, 80)
    else -> minOf(120, configDelay)
  }
}
```

**修改后** (固定值):

```typescript
// VS Code
const fixedDelay = Math.max(120, debounceDelay);
```

```kotlin
// IntelliJ
val fixedDelay = maxOf(120L, configDelay)
```

**设计理由**:

- `max(120, configDelay)` — 下限 120ms，用户配置更大则用用户值
- 120ms 足以合并连续打字的第二键（~60-100ms 到达），拦住绝大部分伪请求
- 真实单字符编辑仅增加 ~90ms 感知延迟（相比原 30ms），可接受
- 偶尔漏网的并发请求由 CompletionStreamer epoch 控制兜底
- 原自适应代码保留为注释，便于回滚参考

**根因评估**: ✅ 简化。与 epoch latest-only 配合后，debounce 只需做"合并毫秒级连续击键"这一件事，固定值足矣。
